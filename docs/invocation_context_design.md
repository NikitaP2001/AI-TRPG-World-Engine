# Agent Invocation Context Design

*Per-agent invocation context, summaries as pinned cache,
news as invocation-scoped input.*

---

## §0 Full Agent Context Structure

Every agent's full prompt is assembled from four layers, from most stable to
most volatile:

```
  Layer 0 — System prompt           NEVER changes
    (prompt_text from agents/{agent}/prompt.txt)

  Layer 1 — Pinned context           Cached, trims trigger rebuild
    (PinnedBlockCache in engine/pinned_context.py)
    Blocks: [world_setting], [arc_summaries], [paragraph_summaries],
            [agent_summaries], [character:{name}]

  Layer 2 — Message history          Persisted between invocations
    (messages.json — previous tool calls, close_invocation summaries)

  Layer 3 — Invocation context       BUILT FRESH EVERY CALL
    [reason] — why called
    [newspaper] — what happened since last call
    [tools_available] — tool list for this agent
```

**Invocation context (§3) is only Layer 3.** It is the MINIMAL new information
the agent receives this call. Layers 0-2 are assembled by the existing
PinnedContext + message history systems and are NOT redesigned here.

---

## §1 Separation of Concerns

### 1.1 `invoke_self` — Pure Scheduling

`invoke_self` does one thing: schedule the next invocation of the calling agent.
It does NOT terminate the current invocation.

```
invoke_self(delay_ticks=-1, world_time=-1, comment="")
  → scheduler_queue records request
  → agent continues working
  → no termination effect
```

### 1.2 `close_invocation` — Termination

New universal termination tool. Replaces `invoke_self` as termination for WM/GM,
and replaces forced tool pairs for SM.

```
close_invocation(
  summary="What the agent did this invocation (2-4 sentences)",
  news=["item1", ...],       # optional, max 3 — for higher agent's newspaper
  invoke_self={...}          # optional: schedule next call inline
)
  → ends invocation
  → orchestrator saves summary to agent's own summary file
  → orchestrator appends news to higher agent's news queue
  → if invoke_self provided, also schedules next call
```

### 1.3 News Flow — Accumulation

GM and WM are NOT called every turn. News from lower agents accumulates:

```
Turn 1: SM closes → news → GM's news queue (stored)
Turn 2: SM closes → news → GM's news queue (appended)
Turn 3: GM called → newspaper = entire queue (consumed, cleared)
```

SM is called every turn. GM and WM are called on demand.

News sources:
- `close_invocation.news` from lower agent → appended to queue
- `record_event` with `narrative_flag=True` → added to all higher agents' queues
- `notify_wm` from GM → queued for WM directly

## §2 Per-Agent Summary — Pinned Cache (Already Implemented Pattern)

Summaries use the EXISTING `PinnedBlockCache` mechanism from
`engine/pinned_context.py`. They are Layer 1 — cached, not rebuilt every call.

### 2.1 Existing Pattern (GM)

GM already has `[gm_summaries]` in PinnedContext. It is built by
`build_gm_summaries_block()` from `world/story.py`, cached via
`PinnedBlockCache`, and only rebuilt when the trim counter changes.

```
[gm_summaries] block content:
  List of last N gm_summary entries from messages.json,
  formatted as: "- Y{year} D{day}: {summary_text}"
```

### 2.2 SM Summaries — Same Pattern

SM gets its own pinned block `[sm_summaries]`, built from SM's own message
history. Same mechanism as GM: `build_sm_summaries_block()` reads SM's
messages.json, extracts `close_invocation` summaries, formats them as a list.

Implementation: add `add_sm_summaries()` to `PinnedContext`, called in SM's
`_pinned_summaries()` alongside existing blocks.

### 2.3 WM Summaries — Same Pattern

WM gets its own pinned block `[wm_summaries]`, built from WM's message history
(`game/wm_state/_wm_history.json`). Same mechanism.

Implementation: add `add_wm_summaries()` to `PinnedContext`, called in WM's
context building (currently no pinned context exists for WM — will be added).

### 2.4 Summary Source: close_invocation, Not Separate Tools

Summaries are generated by the LLM in `close_invocation(summary=...)` and saved
to messages.json. The pinned cache then reads them from messages.json. There is
NO separate summary tool — `close_invocation` is the only summary entry point.

This replaces the old `gm_summary_result` tool for GM, and adds summary
generation for SM and WM where none existed before.

### 2.5 Arc + Paragraph Summaries — Untouched

`[arc_summaries]` and `[paragraph_summaries]` in PinnedContext are NOT changed.
They are built from `story.json` by `build_arc_summaries_block()` and
`build_paragraph_summaries_block()`. These blocks are shared by GM and SM
(visible to both via PinnedContext).

## §3 Invocation Context (Layer 3 — Built Fresh Every Call)

### 3.1 WM Invocation Context

```
[reason]                ← invoke_self comment | "initialize_world"
                          | subscription trigger

[newspaper]             ← GM's news queue (accumulated since last WM call)
                          | narrative_flag events since last WM call
                          | notify_wm queue

[tools_available]       ← 19 tools
```

### 3.2 GM Invocation Context

```
[reason]                ← invoke_self comment | "initialize_world"
                          | escalate_to_gm from SM
                          | write_correction from WM
                          | scene pick trigger

[newspaper]             ← SM's news queue (accumulated since last GM call)
                          | narrative_flag events since last GM call
                          | WM corrections queue

[tools_available]       ← 18 tools
```

### 3.3 SM Invocation Context

```
[reason]                ← escalate_to_sm from GM
                          | "run_scene"
                          | turn execution trigger

[newspaper]             ← escalate_to_sm message (direct instruction)
                          | recent events at current location

[tools_available]       ← 12 tools
```

## §4 Entry/Exit Protocol

### 4.1 Invocation Lifecycle

```
1. Orchestrator checks scheduler_queue for due invocations
2. Builds [newspaper] from agent's news queue (consumes queue)
3. Calls agent with: layers 0-3 assembled
4. Agent enters ReAct loop (WM/GM) or forced tool call (SM)
5. Agent calls close_invocation(summary, news, invoke_self?)
6. Orchestrator appends summary to messages.json (feeds pinned cache)
7. Orchestrator appends news items to higher agent's news queue
8. Orchestrator schedules next call if invoke_self provided
```

### 4.2 What is Saved to Messages

Only the agent's output (tool calls + close_invocation) is saved to messages.json.
Newspaper, narrative_state, pinned blocks are NOT saved — they are rebuilt on
next call.

```
Saved to messages.json:
  └─ tool call records from ReAct loop
  └─ close_invocation {summary, news, invoke_self}

NOT saved:
  └─ [newspaper]               — consumed on read
  └─ [reason]                  — rebuilt from trigger source
  └─ pinned blocks (Layer 1)   — cached/rebuild on trim
```

## §5 close_invocation Detail

```
close_invocation(
  summary="What the agent did (2-4 sentences for future summarization)",
  news=[],         # optional str list, max 3 items
  invoke_self={}   # optional: {delay_ticks or world_time, comment}
)
```

The `summary` field is the ONLY source for the agent's summary block in
PinnedContext. It must be self-contained because it will be read back by the
same agent on future calls.

Examples:
- WM: "Created merchant guild faction. Defined 3 initial trade routes."
- GM: "Set scene at tavern. Created NPC Bob. Resolved negotiation."
- SM: "Ran tavern negotiation. Players agreed to deliver supplies for 50g."

## §6 GM invoke_self + Triggers

GM has the same `invoke_self` as WM. Triggers:
1. `invoke_self` — self-scheduled
2. `escalate_to_gm` from SM — question from scene (blocking)
3. `write_correction` from WM — WM correction
4. Scene pick trigger — new scene needed

## §8 Location Entity Model

### 8.1 Motivation

Current `set_entity` supports only `{"inside": id}`, `{"near": id}`, `{"coords": [x,y,z]}` for positioning. This is insufficient for scene-level spatial reasoning:

- SM needs to know *where* within a tavern an NPC stands (at the bar? by the door?)
- GM needs to define entrances/exits between locations (locked door? hidden passage?)
- Distance calculations between entities in the same location require relative coordinates

### 8.2 Location Entity Format

```yaml
Entity type="location":

  facts: "A two-storey stone tavern with a slate roof..."
  # Prose description — used by SM for scene narration

  stats:
    size: {width: 20, length: 15, unit: "meter"}
    # Physical footprint for spatial queries

  position:
    coords: [lat, lon, alt]     # Absolute world position (for map)
    parent: "loc_district"      # Parent location (hierarchy)
    # If no parent → region-level location on the world map

  connections:                   # NEW — directed edges between locations
    - to: "loc_tavern_kitchen"
      type: "door"              # door | passage | stairs | window | gate | secret
      position: {"relative": [18, 7]}
      # Where the connection IS in this location's coordinate space
      name: "Kitchen door"
      locked: false              # Optional: lock state
      key_id: ""                 # Optional: entity_id of key

    - to: "loc_tavern_upper"
      type: "stairs"
      position: {"relative": [3, 12]}
      name: "Stairs to upper floor"

  sublocations: ["loc_tavern_kitchen", "loc_tavern_upper"]
  # Direct children for hierarchy queries
```

### 8.3 Relative Positioning Within Locations

Entities inside a location can specify *where*:

```yaml
Entity position:
  inside: "loc_sirens_rest"       # Which location
  relative: [4.5, 2.0]           # x, y meters from location origin
  facing: "south"                # Optional: facing direction
```

Origin convention: `(0, 0)` = north-west corner of the location.
GM defines orientation when creating the location via `set_entity`.

### 8.4 GM Creates Locations

No special tool needed — GM uses existing `set_entity(type="location", ...)`:

```
set_entity(
  type="location",
  id="loc_hidden_cave",
  facts="A damp limestone cave with glowing mushrooms...",
  stats={"size": {"width": 10, "length": 30, "unit": "meter"}},
  position={"parent": "loc_mountain_range", "coords": [48.2, -1.5, 0]},
  connections=[
    {"to": "loc_mountain_pass", "type": "passage",
     "position": {"relative": [5, 0]}, "name": "Narrow tunnel"}
  ]
)
```

### 8.5 Tool Impact

- `set_entity` — unchanged signature, but GM now includes `connections` in `stats` dict
- `query_entities` — can filter by `position.inside` to find entities in a location
- `get_scene` — SM tool, returns location + entities inside + connections
- No new tools needed for location management

## §9 NPC/Entity Detailization — Matching Character Depth

### 9.1 What Exists Today — Three Storage Systems, Three Tool Philosophies

**Character files** (`game/characters/{name}/` — 5 files + metadata):

| File | Nature | Update Frequency | Tool to Write |
|---|---|---|---|
| `description.json` | static | never | `update_character_json(pointer, value)` — partial via JSON Pointer |
| `state.json` | dynamic | every scene | `set_character_state(data)` — **full replacement only** |
| `skills.json` | semi-dynamic | milestones | `set_character_skills(data)` — **full replacement only** |
| `equipment.json` | semi-dynamic | loot changes | `set_character_equipment(data)` — **full replacement only** |
| `memory.json` | dynamic | character agent | character agent internal |
| `metadata.json` | trivial | rarely | `set_character_last_acted()` |

JSON Pointer pattern exists for `description.json`: `update_character_json(name, "/personality/traits", "brave")` updates one nested field. The pointer `"-"` appends to arrays. But state/skills/equipment have **no partial updates** — to add one gold coin you must read→modify→write the entire 2KB equipment.json.

**Old NPC/World files** (`game/world/npc.json`, `locations.json`):
- `update_npc_json(name, pointer, value)` — partial via JSON Pointer ✓
- `add_npc_json(name, pointer, value)` — partial with container creation ✓
- `delete_npc_json(name, pointer)` — partial deletion ✓
- Same triple for locations, same triple for character description

**Entity Store** (`game/entity_store/entities.json`):
- `set_entity(id, ...)` — full write (with merge for `gurps` and `stats`)
- `set_entity_facts(id, facts)` — updates only facts field ✓
- `add_tags / remove_tags` — array append/remove ✓
- `set_effect / remove_effect` — array append/remove ✓
- `attach_script / detach_script` — array append/remove ✓
- **No partial update for `state`, `skills`, `equipment`** — don't exist yet
- **No JSON Pointer tools** — the partial update pattern from the old World class was NOT ported to entity_store
- **No array tools for `conditions`, `inventory`, `cached_skills`**

**`update_entity_stat` (SM-only) — has a bug:**
Writes directly to `_load()` cache dict, then calls `set_entity_facts` which only persists the `facts` field. Changes to `gurps`/`stats` are written to the in-memory cache (and thus returned by `get_entity` within the same process) but **NOT saved to disk** on cache flush.

### 9.2 Static vs Dynamic — What Belongs Where

The character files philosophy separates data by **change frequency**:

**Static / Base** (written once per entity lifetime, read every context build):
- `description.json` — personality, race, traits (character only)
- `facts` — prose description (entity_store, for NPCs)
- GURPS core: `ST, DX, IQ, HT` — set at creation, never change
- `passive_abilities` — permanent advantages ("High Pain Threshold")
- `signature` equipment — permanent carried gear
- `narrative_tier`, `origin`, `lore_interpretation_rule`

→ **Tools: `set_entity` (full block). Once set, never touched again.**

**Dynamic State** (changes every scene, may change multiple times per turn):
- `hp, fp, er, will` — current numerical values
- `conditions` — array: `["poisoned", "blinded"]`
- `injuries` — array: `["broken arm", "deep gash on thigh"]`
- `hunger, thirst, fatigue` — ticking counters

→ **Tools: `update_entity_stat` for scalars, `add/remove` for arrays. Must NOT require full block rewrite.**

**Semi-Dynamic / Inventory** (changes occasionally):
- `inventory` — array of items
- `currency` — dict of coin types
- `cached_skills` — LRU list (skills the entity has used recently)
- `equipment.signature` — changes on major milestones

→ **Tools: `add/remove` for item arrays, `update_entity_stat` for currency values.**

**Temporary Effects** (per-scene, auto-expire):
- `effects[]` — timed modifiers: `{"stat_deltas": {"HP": -2}, "duration_ticks": 5}`

→ **Tools: `set_effect / remove_effect` already exist. Missing: distinction between permanent base features and temp effects.**

### 9.3 The Gap: Many Tools vs One Tool

The previous design proposed ~15 new single-purpose tools. That's wrong — it duplicates, bloats the prompt, and forces the agent to choose from too many options.

**What's common between characters and NPCs?** Both are entities with:
- A state block (HP, FP, conditions, injuries)
- A skills block (abilities, cached_skills, GURPS stats)
- An equipment block (inventory, currency)
- Effects (temporary modifiers)

The difference is only `backend`: characters live in `game/characters/{name}/*.json`, NPCs live in `entity_store`. The agent shouldn't care — one tool should handle both.

### 9.4 Unified Tool: `adjust_entity`

One tool to replace all partial-update functions. Follows the same style as existing WM/GM tools (detailed docstring, named parameters, explicit args).

```python
@tool
def adjust_entity(
    entity_id: str,
    # ── State mutations (HP/FP/conditions/injuries) ──
    hp: Optional[int] = None,
    fp: Optional[int] = None,
    er: Optional[int] = None,
    add_condition: str = "",
    remove_condition: str = "",
    add_injury: str = "",
    remove_injury: str = "",
    # ── Inventory mutations (items + currency) ──
    add_item: str = "",
    remove_item: str = "",
    currency_delta: Optional[Dict[str, int]] = None,
    # ── Skills mutations (abilities + skill list) ──
    add_ability: str = "",
    remove_ability: str = "",
    add_skill: str = "",
    remove_skill: str = "",
    # ── Narrative ──
    current_state: str = "",
) -> Dict[str, Any]:
    """Apply targeted runtime mutations to an entity (NPC or character).

    Unlike *set_entity* (which creates or overwrites static blocks), this
    tool is for the small, frequent changes that happen during gameplay
    — a condition gained, an item picked up, HP lost, a skill learned.

    Every parameter is optional. Only the provided fields are changed;
    everything else on the entity is left intact. This keeps each call
    small (~200 tokens) instead of requiring a full read→modify→write
    cycle (~2000+ tokens for a complex entity).

    Works for both NPCs (entity_store) and player characters (character
    files). The backend is selected automatically.

    **IMPORTANT — facts vs structured fields:**
    Do NOT put mechanical data (HP, GURPS stats, inventory, conditions)
    into `facts`. `facts` is static narrative identity only — it appears
    in the agent's pinned context and must survive trimming. Everything
    mechanical or dynamic has its own parameter below.

    Args:
        entity_id: Target entity id (e.g. "npc_guard", "Elena Brightwood").

        hp: New HP value (absolute set, not delta).
            Use when damage or healing resolves.
        fp: New FP value (absolute set).
        er: New ER value (absolute set).

        add_condition: Append one condition (e.g. "poisoned", "blinded").
            Idempotent — adding a duplicate is a no-op.
        remove_condition: Remove one condition by exact name.
            No-op if the condition is not present.

        add_injury: Append one injury (e.g. "broken rib").
        remove_injury: Remove one injury by exact name.

        add_item: Append one item to inventory (e.g. "gold coin").
        remove_item: Remove one item from inventory by exact name.

        currency_delta: Delta map — positive = gain, negative = loss.
            E.g. {"gold": -5, "silver": 10} spends 5 gold, gains 10 silver.
            Only these coin types are changed; others are untouched.

        add_ability: Append one passive ability (e.g. "Night Vision").
            Passive abilities are permanent — use add/remove, never rewrite.
        remove_ability: Remove one passive ability by exact name.

        add_skill: Append one cached skill (e.g. "Stealth-14").
        remove_skill: Remove one cached skill by exact name.

        current_state: Short one-line description of what the entity
            is doing right now (e.g. "tending bar", "standing guard").
            Overwrites any previous current_state.

    Returns:
        Dict with:
            entity_id: The target entity.
            mutations_applied: List of what was changed.
            state: The resulting state block summary (HP/FP + condition count).
    """
```

### 9.5 What `adjust_entity` Replaces

| Proposed Earlier (discarded) | Replaced By |
|---|---|
| `set_entity_state` | `adjust_entity(hp=..., fp=...)` |
| `add_entity_condition` | `adjust_entity(add_condition=...)` |
| `remove_entity_condition` | `adjust_entity(remove_condition=...)` |
| `add_entity_item` | `adjust_entity(add_item=...)` |
| `remove_entity_item` | `adjust_entity(remove_item=...)` |
| `add_entity_ability` | `adjust_entity(add_ability=...)` |
| `remove_entity_ability` | `adjust_entity(remove_ability=...)` |
| `update_entity_stat` (SM, buggy) | `adjust_entity(hp=..., fp=...)` |
| JSON pointer tools | **Not needed** — abstracted away |

Total: **1 tool** instead of ~15. The agent reads one docstring and has full power.

### 9.6 Backend Selection — Characters vs NPCs

The single `adjust_entity` tool works on BOTH:

| If `entity_id` matches... | Backend | Written to |
|---|---|---|
| A character name (case-insensitive, from `game/characters/{name}/`) | Character filesystem | `state.json`, `skills.json`, `equipment.json` |
| An entity_store id | entity_store | `entities.json` |

The agent never needs to know where the data lives. The tool checks: "is this a character name?" If yes → filesystem backend. If no → entity_store backend.

Three backends converge to one interface:

```
character files  ─┐
entity_store    ──┤── adjust_entity(entity_id, ...)
old npc.json    ──┘  (future: route to any backend)
```

### 9.7 Entity Schema — Final

The entity in `entities.json` gains 3 optional blocks mirroring character files:

```python
{
  "id": "npc_marta",
  "type": "npc",

  # === STATIC NARRATIVE IDENTITY (survives into pinned context) ===
  # facts = who/what this entity IS. NOT current state, NOT mechanics.
  # Everything in facts appears in agent's context — keep it lean.
  "facts": "Marta Haskel, stout woman in her mid-fifties...",
  "gurps": {"ST": 10, "DX": 10, "IQ": 11, "HT": 10},

  # === DYNAMIC STATE (mutated by adjust_entity) ===
  "state": {                            # OPTIONAL — mirrors state.json
    "hp": 10, "max_hp": 10,
    "fp": 10, "max_fp": 10,
    "er": 0, "max_er": 0,
    "will": 11,
    "conditions": ["frightened"],       # adjust_entity add/remove_condition
    "injuries": [],                     # adjust_entity add/remove_injury
    "hunger": 0, "thirst": 0, "fatigue": 0
  },

  # === SKILLS (semi-dynamic) ===
  "skills": {                           # OPTIONAL — mirrors skills.json
    "ST": 10, "DX": 10, "IQ": 11, "HT": 10,
    "narrative_tier": "average",
    "passive_abilities": ["High Pain Threshold"],   # adjust_entity add/remove_ability
    "cached_skills": ["Savoir-Faire-13"],            # adjust_entity add/remove_skill
    "lore_interpretation_rule": "Marta knows the docks..."
  },

  # === EQUIPMENT (semi-dynamic) ===
  "equipment": {                        # OPTIONAL — mirrors equipment.json
    "signature": ["Bar rag"],            # static — set with set_entity
    "inventory": ["Cellar keys"],        # adjust_entity add/remove_item
    "currency": {"gold": 5, "silver": 12}  # adjust_entity currency_delta
  },

  # === FREE-FORM ===
  "stats": {},
  "tags": ["role:barkeep"],
  "position": {"inside": "loc_sirens_rest", "relative": [4.0, 2.0]},

  # === RUNTIME ===
  "scripts": [],
  "effects": [{"effect_id": "poison_01", "stat_deltas": {"HP": -1}, "per_tick": True, "duration_ticks": 5}],
  "movement": null,
  "created_at": "...",
  "updated_at": "..."
}
```

### 9.8 Entity/Character Common Structure

| Character File | Entity Field | Written By |
|---|---|---|
| `description.json` | `facts` | `set_entity(id, facts=...)` — creation |
| `state.json` | `state` | `adjust_entity(hp=..., fp=..., add_condition=...)` |
| `skills.json` | `skills` | `set_entity(id, skills=...)` for bulk, `adjust_entity(add_ability=...)` for single |
| `equipment.json` | `equipment` | `adjust_entity(add_item=..., currency_delta=...)` |
| `memory.json` | *(NPCs don't have this)* | GM updates `facts` if NPC needs narrative memory |
| `metadata.json` | *(not ported)* | Not relevant |

### 9.9 Workflow Examples

**Create a minimal NPC (one tool call):**
```
set_entity(type="npc", facts="A guardsman. Bored. Leaning on a spear.")
```
→ NPC exists. SM can reference it.

**Detailize during gameplay (one `adjust_entity` call per change):**
```
# Before combat — add HP + skills
adjust_entity("npc_guard", hp=12, fp=10)
adjust_entity("npc_guard", add_skill="Spear-12")

# During combat — take damage + gain condition
adjust_entity("npc_guard", hp=4, add_condition="stunned")

# After combat — players search the body
adjust_entity("npc_guard", add_item="Copper piece (3)")

# Clean up
adjust_entity("npc_guard", remove_condition="stunned")
```

Each call is a single tool invocation. No read-modify-write cycle. The agent doesn't touch JSON paths, doesn't know about files, doesn't manage backends.

### 9.10 What Still Uses `set_entity` (Not `adjust_entity`)

`set_entity` remains the creation and static-block tool:

| Use Case | Tool |
|---|---|
| Create a new NPC | `set_entity(type="npc", facts=..., gurps=..., skills=..., equipment=...)` |
| Create a location | `set_entity(type="location", facts=..., stats=..., position=...)` |
| Rewrite facts entirely | `set_entity_facts(id, facts)` |
| Set tags | `add_tags / remove_tags` |
| Set effects | `set_effect / remove_effect` |
| Attach scripts | `attach_script / detach_script` |
| **Runtime mutations** (HP, items, conditions) | **`adjust_entity`** |

### 9.11 Implementation Plan

**Phase A — entity_store backend:**
1. Add `state`, `skills`, `equipment` fields to `set_entity()` — optional, default `{}`
2. Implement `adjust_entity()` in `entity_store.py` — handles all mutation types
3. Backend stores mutations in the respective entity block

**Phase B — Character file backend:**
4. Same `adjust_entity()` implementation writes to `game/characters/{name}/*.json`
5. Auto-detect backend: character name → filesystem, else → entity_store

**Phase C — Wire as tools:**
6. Add `adjust_entity` to `world_manager/tools.py` (WM)
7. Add `adjust_entity` to `gm/tools.py` (GM)
8. Add `adjust_entity` to `scene_manager/tools.py` (SM) — restricted: no skills/abilities mutations
9. Fix `update_entity_stat` bug — delegate to `adjust_entity` internally

**Phase D — Remove redundancy:**
10. SM gets `adjust_entity` with only state/inventory mutations (no skills)
11. SM keeps `get_entity_state` (extended to return `state` block)
12. `update_entity_stat` becomes a thin wrapper around `adjust_entity` (or removed)

### 9.12 Not In Scope

- **NPC memory** — not needed. WM/GM append narrative memory by updating `facts`.
- **Auto-promote NPC → character** — manual. GM creates character folder.

## §10 Script Runtime — `attach_script` with Full Agent Tool Access

### 10.1 Current State: Scripts Are Dead Text

Currently `attach_script` stores a Python string on the entity. There is NO execution
engine. The script is never run. The design document lists it only as "array append/remove"
with no specification of runtime behaviour.

This is wrong. Scripts are the **automation layer** of the simulation — they should
execute on triggers and call the **same tools** the agent would call.

### 10.2 Design: Script Runtime

Each script is a Python function that runs in a sandbox with access to the full
entity_store API (the same backend functions that power WM/GM/SM tools):

```python
# Stored on entity:
{
    "script_id": "aura_despair_001",
    "trigger_type": "on_tick",           # what causes execution
    "trigger_params": {"interval_ticks": 1},
    "script": "def run(ctx): ...",       # executable code
    "comment": "Aura of Despair"
}
```

When a trigger fires, the runtime:
1. Loads the script from the entity
2. Creates a `ctx` context dict with: `entity_id`, `world_time`, `trigger_params`
3. Injects the tool API functions into the script's namespace
4. Executes `run(ctx)` — script calls tools freely
5. Collects results — script can schedule itself via `invoke_self` in ctx

### 10.3 Tools Available Inside Scripts

The following backend functions are injected into every script's global namespace.
These are the **exact same implementations** that back the agent tools:

| Injected Name | Backed By | Description |
|---|---|---|
| `get_entity(id)` | `entity_store.get_entity` | Read any entity |
| `get_entity_facts(id)` | `entity_store.get_entity_facts` | Read facts only |
| `query_entities(type, tags, position, radius)` | `entity_store.query_entities` | Search entities |
| `set_entity_facts(id, facts)` | `entity_store.set_entity_facts` | Update facts |
| `set_effect(entity_id, stat_deltas, duration_ticks, aura_radius)` | `entity_store.set_effect` | Apply effect |
| `remove_effect(entity_id, effect_id)` | `entity_store.remove_effect` | Remove effect |
| `add_tags(entity_id, tags)` | `entity_store.add_tags` | Add tags |
| `remove_tags(entity_id, tags)` | `entity_store.remove_tags` | Remove tags |
| `record_event(description, entity_ids, tag, narrative_flag)` | `event_log.record_event` | Write event |
| `adjust_entity(entity_id, hp=..., fp=..., add_condition=..., add_item=...)` | `entity_store.adjust_entity` | Mutate entity (see §9.4) |

**What scripts do NOT have access to:**
- `set_entity` (creation — agent-only)
- `delete_entity` (destruction — agent-only)
- `invoke_self` / scheduler (agent-only, but scripts can return `reschedule` in their result)
- `close_invocation` (agent-only)
- LLM calls, file I/O, network, imports beyond stdlib

### 10.4 Trigger Types and Execution

| Trigger | `trigger_params` | When Script Runs |
|---|---|---|
| `on_tick` | `{"interval_ticks": N}` | Every N world ticks |
| `on_stat_threshold` | `{"stat": "hp", "threshold": 3, "direction": "below"}` | When stat crosses threshold |
| `on_entity_enter` | `{"tag_filter": "npc", "radius": 10}` | When matching entity enters radius |
| `on_event_nearby` | `{"tag_filter": "combat", "radius": 20}` | When matching event occurs nearby |
| `on_world_time` | `{"tick": 5000}` | Once at exact world tick |
| `on_tag_added` | `{"tag": "wounded"}` | When tag is added to the entity |

### 10.5 Aura of Despair — Complete Workflow (GM's View)

**Step 1 — Create the lich with narrative context:**
```python
set_entity(
    type="npc", id="lich_villain",
    facts="Ancient lich of terrifying power. Radiates despair.",
    skills={"passive_abilities": ["Aura of Despair"]},
    gurps={"ST": 14, "DX": 12, "IQ": 18, "HT": 16},
    tags=["boss", "undead", "spellcaster"]
)
```

**Step 2 — Attach the automated aura script:**
```python
attach_script(
    entity_id="lich_villain",
    trigger_type="on_tick",
    trigger_params={"interval_ticks": 1},
    script="""
def run(ctx):
    nearby = query_entities(
        position={"inside": ctx["entity_id"]},
        radius=10.0
    )
    for e in nearby:
        if "undead" not in (e.get("tags") or []):
            set_effect(
                entity_id=e["id"],
                effect_id="despair_aura",
                stat_deltas={"will": -2},
                per_tick=True,
                duration_ticks=2,
                description="Aura of Despair (lich)"
            )
    return {"applied": len(nearby)}
""",
    comment="Aura of Despair — Will-2 to all living entities within 10m"
)
```

**Step 3 — The script fires every tick. The runtime:**
1. Calls `query_entities(position={"inside": "lich_villain"}, radius=10.0)`
2. For each non-undead entity found, calls `set_effect(will=-2, duration_ticks=2)`
3. Duration 2 ticks means the effect refreshes every tick — it never expires while the lich is nearby
4. If the lich moves away, the effect expires naturally after 2 ticks

**Step 4 — Cleanup (when lich is defeated / aura removed):**
```python
detach_script(entity_id="lich_villain", script_id="aura_despair_001")
```

### 10.6 Script Runtime Constraints and Safety

- **Execution timeout:** 100ms per script call. Hanging scripts are killed.
- **No loops without limits:** `query_entities` has a built-in `limit=50` for spatial queries.
- **No disk I/O, no network, no imports beyond stdlib.**
- **Scripts can't create or delete entities** — only mutate existing ones.
- **Scripts can't call LLM** — they are pure logic.
- **Result is logged** to event_log with `tag="script_result"`.

### 10.7 Relation to `set_effect` with `aura_radius`

The `set_effect` aura_radius proposal from the previous discussion is a **subset**
of `attach_script`. For simple auras (stat debuff in radius), `set_effect(aura_radius=N)`
is a shortcut — the engine internally creates a script that does exactly step 2.

| If you need... | Use |
|---|---|
| Simple stat debuff in radius | `set_effect(aura_radius=10, stat_deltas={"will": -2})` — engine auto-generates script |
| Conditional logic ("only apply to living, not undead") | `attach_script` with explicit `query_entities` |
| Multi-step effects ("apply debuff + spawn minion") | `attach_script` |
| Effects that depend on entity properties ("more debuff to elves") | `attach_script` |

Both are valid. `set_effect(aura_radius=...)` is syntactic sugar for common cases.
